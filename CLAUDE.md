# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

oh8oh — a Bangalore events aggregator PWA. TanStack Start (React SSR) deployed to Cloudflare Workers via Nitro. Events come from web scrapers plus user submissions, stored in a Turso (libsql) database via Drizzle ORM.

## Commands

```bash
pnpm dev              # Vite dev server on http://localhost:3000 (fast; no Cloudflare bindings — R2/BROWSER unavailable)
pnpm build            # Production build to .output/ (also copies PWA sw.js/workbox files from dist/)
pnpm dev:wrangler     # Run the built output in wrangler with real bindings (run pnpm build first)
pnpm test             # vitest run
pnpm vitest run path/to/file.test.ts   # single test file
pnpm check            # prettier --write . && eslint --fix (use this before committing)
pnpm lint             # eslint only
pnpm db:generate      # drizzle-kit generate (migrations output to drizzle/)
pnpm db:migrate       # drizzle-kit migrate against Turso (needs TURSO_* set in the shell)
pnpm db:studio        # Drizzle Studio
pnpm cf:deploy        # build with prod VITE_AUTH_URL, then wrangler deploy from .output/ (relies on shell-emulator in .npmrc for the VAR=x syntax on Windows)
```

## Gotchas

- **The database is Turso, not D1.** [src/db/index.ts](src/db/index.ts) connects via `drizzle-orm/libsql/http` using `TURSO_DATABASE_URL` / `TURSO_AUTH_TOKEN` (falls back to `file:local.db`), and [drizzle.config.ts](drizzle.config.ts) uses the `turso` dialect. There is no D1 binding; migrations are applied to Turso with drizzle-kit.
- `src/routeTree.gen.ts` is generated by the TanStack Router plugin — never edit it by hand.
- Env vars must be read through the `getEnv()` pattern (check `process.env`, then `globalThis.__env__`) because Nitro on Cloudflare Workers exposes bindings/secrets via `globalThis.__env__`, not `process.env`. See [src/db/index.ts](src/db/index.ts) and [src/lib/auth.ts](src/lib/auth.ts).
- `db` and `auth` are exported as lazy Proxy singletons so nothing touches env at module-evaluation time (Workers constraint). Follow the same pattern for new module-level resources.
- [nitro.config.ts](nitro.config.ts) injects a `Reflect.metadata` polyfill banner and uses the `cloudflare-module` preset only when `NODE_ENV=production`. Workers-compat settings there (export conditions, wasm disabled) are load-bearing.

## Architecture

### Runtime layout

- **Routes**: file-based in `src/routes/` (TanStack Router). API routes are file routes with `server.handlers` — the Better Auth catch-all is [src/routes/api/auth/$.ts](src/routes/api/auth/$.ts). There is no HTTP scrape trigger: the daily full scrape runs from a Cloudflare Cron Trigger (`[triggers]` in wrangler.toml) handled by the Nitro plugin [src/lib/cron/scheduled-scrape.ts](src/lib/cron/scheduled-scrape.ts).
- **Server functions**: `createServerFn` handlers live in `src/lib/server/` (bookmarks, user events, event fetching, manual refresh). Resolve the user with the helpers in [src/lib/server/session.ts](src/lib/server/session.ts) (`requireUser`/`requireRole`), and get Cloudflare bindings with `getCloudflareEnv(ctx)` / `getWaitUntil(ctx)` from the same file — the server-function `ctx.context` does **not** carry the Cloudflare env; Nitro puts it on the request and on `globalThis.__env__`.
- **Cloudflare bindings** (wrangler.toml): `R2` (image uploads, see [src/lib/r2-upload.ts](src/lib/r2-upload.ts)), `BROWSER` (Browser Rendering for Puppeteer scrapers), `ASSETS`. Secrets via `wrangler secret put`: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`, `RESEND_API_KEY`, `RESEND_FROM_EMAIL`. `R2_PUBLIC_URL` is a plain var in wrangler.toml.

### Scraper pipeline (the core data flow)

1. Each source has a scraper in `src/lib/scrapers/` implementing the `EventScraper` interface ([types.ts](src/lib/scrapers/types.ts): `id`, `name`, `website`, `enabled`, optional `priority`, `scrape(env)`). New scrapers must be registered in the array in [src/lib/scrapers/index.ts](src/lib/scrapers/index.ts).
2. `scrapeAllSources()` runs high/normal-priority scrapers in parallel, then low-priority (Puppeteer via `BROWSER` binding, see [browser-helper.ts](src/lib/scrapers/browser-helper.ts)) sequentially with a 60s per-scraper timeout. `FAST_SCRAPER_IDS` defines the subset used for quick refreshes.
3. Results are fuzzy-deduplicated across sources ([deduplicate-events.ts](src/lib/utils/deduplicate-events.ts) merges near-duplicate titles/dates) and upserted into the `events` table in batches; each run is recorded in `scraper_runs`. Full runs also prune long-finished events (`pruneStaleEvents`).
4. [src/lib/cache/events-cache.ts](src/lib/cache/events-cache.ts) is the read path: it always returns the not-yet-ended DB events immediately, and kicks off a non-blocking fast-scraper refresh when the last run is >30 minutes old. That refresh must be registered with `waitUntil` or Workers cancel it. Full scrapes (including Puppeteer) only happen via the daily Cron Trigger or the admin's explicit full refresh.

### Dates

Scraped dates are free-form strings stored as-is (changing a stored date string changes the event's id and fingerprint, so don't normalise them in place). `getEventDates()` in [src/lib/utils/date-time.ts](src/lib/utils/date-time.ts) is the single function that turns one into a start and end day; filters, sorting, the calendar, the .ics export and the displayed date all go through it — don't add another parser. "Today" is always Bangalore time (IST), on server and client. Tests are in `date-time.test.ts` and `calendar.test.ts`.

### Event identity

Scraped events have no stable upstream IDs, so events are identified by a **fingerprint** — a hash of normalized title + date + link ([src/lib/utils/event-fingerprint.ts](src/lib/utils/event-fingerprint.ts)). Event detail pages route by it (`src/routes/event.$fingerprint.tsx`), bookmarks snapshot full event data (since scraped rows can vanish on re-scrape), and admin removals are recorded in `removed_events` by fingerprint so re-scraped events stay hidden.

### Auth and roles

Better Auth with the Drizzle adapter ([src/lib/auth.ts](src/lib/auth.ts)): email/password with **required email verification**, emails sent through Resend with react-email templates in `src/lib/emails/`. Passkey and Google social login are scaffolded but commented out. Users have a `role` (`admin` | `host` | `user`) stored on the `user` table; permission helpers are in [src/lib/roles.ts](src/lib/roles.ts) (`isHost` includes admins). Hosts/admins submit events into `user_events` with an approval workflow (`draft`/`pending`/`approved`/`rejected`, plus `featured`), moderated at `src/routes/admin/review-events.tsx`.

### Frontend conventions

- Path alias `@/*` → `src/*`.
- shadcn/ui components in `src/components/ui/` (Radix + class-variance-authority, configured via components.json); app components in `src/components/`.
- Tailwind CSS 4 (via `@tailwindcss/vite`, no tailwind.config file); theming via next-themes.
- PWA is configured in [vite.config.ts](vite.config.ts) (vite-plugin-pwa, prompt-based updates, `/api/` never cached); it is disabled during SSR builds via `VITE_ENVIRONMENT=ssr`.
